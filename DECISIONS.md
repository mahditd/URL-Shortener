# Design decisions

## Dependencies

No additional direct dependencies were used outside the allowed web framework (Gin) and GORM with its PostgreSQL driver.

## Part 1

- URL normalization:
  Two URLs are considered the same after normalization.

  The normalization process:
  - Removes surrounding whitespace.
  - Converts the URL scheme and host to lowercase.
  - Removes default ports:
    - `:80` for HTTP.
    - `:443` for HTTPS.
  - Validates that only `http` and `https` schemes are accepted.

  Paths, query parameters, and fragments are preserved because they may represent different resources.

- Same URL → same code:
  The application checks whether a normalized URL already exists before generating a new code.

  The repository stores both:
  - normalized long URL
  - generated short code

  If the URL already exists, the existing code is returned.

- Code generation:
  New URLs receive a randomly generated 6-character alphanumeric code.

  Codes contain only:
  - lowercase letters
  - uppercase letters
  - numbers

  Code generation happens only for URLs that do not already exist.

- Collision handling:
  Generated codes are checked through the repository before being returned.
  If a collision occurs, generation is retried until a unique code is found.

- Mutex and locking:
  The in-memory repository uses `sync.RWMutex`.

  Lock usage:
  - `Save()` uses `Lock()` because it modifies shared state.
  - `FindByCode()` uses `RLock()` because it only reads data.
  - `FindByURL()` uses `RLock()` because it only reads data.

  RWMutex was chosen because redirect and lookup operations are expected to occur more frequently than writes.

- Package layout:
  The project follows a Clean Architecture style:
  - `domain`
    - Entities
    - Domain errors
    - Repository interfaces

  - `application`
    - Use cases
    - DTOs
    - Business rules

  - `infrastructure`
    - Database connection
    - Repository implementations
    - Persistence models

  - `presentation`
    - HTTP controllers
    - Routes

  - `bootstrap`
    - Dependency wiring

  - `cmd/server`
    - Application entry point

## Part 2

- Store interface:
  The repository abstraction is defined in:

  `internal/domain/ports/link_repository.go`

  The interface exposes:
  - `Save(link entities.Link)`
  - `FindByCode(code string)`
  - `FindByURL(url string)`

  The use case depends on this abstraction instead of a concrete storage implementation.

- Error handling:
  Domain errors are represented using sentinel errors:
  - `ErrNotFound`
  - `ErrInvalidURL`

  Errors are wrapped using `%w` to preserve their identity.

  HTTP handlers use `errors.Is()` to map errors into responses:
  - `ErrInvalidURL` → `400 Bad Request`
  - `ErrNotFound` → `404 Not Found`
  - Unknown errors → `500 Internal Server Error`

  Error responses are returned as JSON objects containing an `error` field.

## Part 3

- Locking choice:
  The in-memory store uses `sync.RWMutex`.

  Redirect and lookup operations only require read access, allowing multiple concurrent readers.

  Write operations acquire exclusive access to prevent race conditions.

- Timeout values:
  The HTTP server uses:
  - `ReadTimeout`: 5 seconds
  - `WriteTimeout`: 10 seconds
  - `IdleTimeout`: 60 seconds

  These values prevent slow clients from occupying server resources indefinitely.

- Eviction:
  No eviction policy is implemented.

  The assignment does not require a maximum in-memory capacity, so links remain available while the application process is running.

## Part 4

- Storage choice:
  PostgreSQL was selected as the persistent storage solution.

  GORM is used as the ORM layer to simplify database interaction while keeping the repository abstraction independent from the database.

- Schema and models:
  The database contains a `links` table.

  Model fields:
  - `id`
    - Primary key generated by the database.

  - `url`
    - Original long URL.
    - Unique index prevents duplicate URLs.

  - `code`
    - Generated short code.
    - Unique index prevents collisions.

  - `created_at`
    - Creation timestamp.

  Database schema creation is handled using GORM AutoMigrate.

- Crash safety and atomicity:
  The application only returns a successful shorten response after the database insertion succeeds.

  PostgreSQL provides durable storage, ensuring saved links survive application restarts.

- Created timestamp:
  Creation time is stored using Go's `time.Time` type and persisted by GORM in the database `created_at` column.

- Idempotency after restart:
  URL-to-code mappings are stored in PostgreSQL.

  After restarting the application, a new repository instance can retrieve existing records, so the same normalized URL continues returning the same short code.

## Part 5

### Stateless Application and Shared Storage

The application is designed to support horizontal scaling by keeping application instances stateless.

A production deployment can run multiple Go application replicas behind a load balancer:

Client → Load Balancer → Multiple Go Instances → Shared PostgreSQL Database

When using shared persistent storage, application instances do not store persistent link data locally.

When deployed with PostgreSQL storage, PostgreSQL acts as the shared source of truth for URL mappings. This allows any application instance to process shorten and redirect requests while maintaining consistent data.

The main tradeoff of this approach is increased operational complexity. Running multiple application instances requires infrastructure for service discovery, load balancing, and database availability management.

### Write Path Scaling

The URL creation endpoint is protected by rate limiting to prevent excessive write traffic.

The current implementation limits requests to:

- 10 requests per minute
- Per client IP address

This reduces abuse and protects application resources during high traffic periods.

For larger-scale deployments, the rate limiter could be moved to a shared store such as Redis so that limits are enforced consistently across multiple application instances.

### Future Read Path Improvements

For very high traffic redirect workloads, a CDN or edge cache could be introduced to cache frequently accessed redirect responses.

Caching 302 redirects reduces load on application servers and PostgreSQL.

The main tradeoff is cache consistency. If a URL mapping is modified or removed, cached redirects may remain available until the cache TTL expires.

### Future Database Scaling

If the number of stored links becomes too large for a single PostgreSQL instance, the database can be partitioned or sharded.

Possible strategies include partitioning by code prefix or distributing records using consistent hashing.

The tradeoff is increased system complexity because queries, migrations, and operational tasks become more difficult in a distributed database environment.

## Part 6

### Graceful Shutdown

The application implements graceful shutdown using Go's `signal.Notify` and `http.Server.Shutdown`.

When the process receives `SIGINT` or `SIGTERM`, the server stops accepting new connections and waits for existing in-flight requests to complete.

A shutdown timeout of 5 seconds is used. If active requests do not finish within this period, the server terminates to avoid waiting indefinitely.

This approach prevents abruptly terminating active requests while still allowing controlled shutdown behavior.

### Rate Limiting

The `POST /api/shorten` endpoint is protected by a rate limiter middleware.

The current configuration allows:

- 10 requests per minute
- Per client IP address

The limiter is implemented in memory and is protected with synchronization to support concurrent requests safely.

The tradeoff is that the current limiter works only inside a single application instance. In a multi-instance deployment, a shared rate limiting solution such as Redis would be required to enforce limits globally.

### Logging and Observability

The application avoids logging complete user-provided URLs because URLs may contain sensitive information such as tokens or private query parameters.

Future production deployments can add structured logging and metrics collection for:

- Request rate
- HTTP errors
- Response latency
- Redirect success/failure rates

These metrics would improve monitoring while avoiding exposure of sensitive URL data.
